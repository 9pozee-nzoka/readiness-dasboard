1. Project Overview

The Weekly Event Readiness Dashboard is a purpose-built web application designed to help organisations track and manage departmental readiness ahead of weekly events. Instead of relying on fragmented email chains, spreadsheets, or ad-hoc meetings, every department's preparation status is visible in real time on a single, role-aware dashboard. Coordinators, heads of department, and executives all see the information most relevant to them, at the level of detail they need.

The core problem the system solves is accountability. Each department is assigned a set of requirements for every upcoming event. Those requirements have priorities, deadlines, and responsible officers. The dashboard aggregates completion state into RAG (Red/Amber/Green) indicators and weighted readiness percentages, so decision-makers can identify at-risk events before they become crises rather than after.

Key Design Decisions

  • No SPA framework: The UI is rendered server-side with Blade templates. Alpine.js handles interactive components (dropdowns, AJAX toggling, chat). This keeps the stack simple and avoids a build-time API layer.
  • Database queues and sessions: Rather than requiring Redis, the application stores queued jobs, cached data, and session payloads in the database. This simplifies deployment on shared hosting and Render's free tier.
  • Role-based access via middleware: A custom RoleMiddleware class checks UserRole enum values against the authenticated user's role. Admin-only routes are grouped under a separate /admin prefix with the role:admin middleware applied at the group level.
  • Weighted readiness scoring: Simple completion percentage (tasks done / total tasks) is complemented by a weighted score that multiplies each requirement's completion state by its priority weight. This prevents a department from appearing "ready" when only low-priority tasks are done while critical ones remain open.
  • Laravel Reverb for real-time chat: The first-party WebSocket server is embedded in the same container as the web application, eliminating the need for a separate Pusher subscription in production.

2. Architecture Overview

The application follows a classic server-rendered MVC architecture with targeted real-time enhancements. There is no client-side routing or state management library; every page load is a full server render, and interactivity is layered on top with Alpine.js and occasional AJAX calls.

Browser (Alpine.js + Blade) | | HTTP/HTTPS (port 8080) v Nginx (reverse proxy) | | FastCGI (Unix socket) v PHP-FPM (Laravel 13) | +-- MySQL / MariaDB (Eloquent ORM) | +-- Database Queue Worker | +-- Laravel Reverb (WebSocket, same port 8080) | | Private Channel: chat-room.{id} v Browser Echo Client (Pusher JS protocol)

Request Lifecycle

An incoming HTTP request flows through Nginx to PHP-FPM. Laravel's kernel runs the global middleware stack (CSRF protection, session, authentication) before routing to the appropriate controller action. Controllers resolve Eloquent models, perform business logic, and return Blade views or JSON responses.

For real-time features, the browser connects a Laravel Echo client to the Reverb WebSocket server. The Echo client uses the Pusher JavaScript protocol so the same client library works whether the backend is Reverb (self-hosted) or Pusher (cloud). When a chat message is sent, the controller dispatches a MessageSent event that implements ShouldBroadcast. Laravel's broadcasting system serialises the event and sends it over the appropriate private channel.

3. Database Schema

The database consists of 38 tables across 38 migration files. The schema was built incrementally: a compact initial set of tables was created in May 2026, with deliberation, audit, asset, and risk tables added in June, and the chat system added in August. All foreign key constraints use cascading deletes where the child record has no independent meaning (e.g., requirements cascade with events), and nullify (set null) where the relationship is optional (e.g., a user can be deleted without removing requirements they were assigned to).

4. Roles & Permissions

Access control is role-based. Four roles are defined as a PHP backed enum (App\Enums\UserRole) and stored as a string column on the users table. Role checking is performed by RoleMiddleware, which reads the comma-separated role list from the middleware parameter string and compares each against the authenticated user's role attribute using UserRole::from().

// app/Http/Middleware/RoleMiddleware.php
public function handle(Request $request, Closure $next, string ...$roles): Response
{
    $user    = $request->user();
    $allowed = collect($roles)->map(fn($r) => UserRole::from($r));

    if (! $allowed->contains($user->role)) {
        abort(403, 'You do not have permission to access this page.');
    }

    return $next($request);
}

Registration & Approval Workflow

New users self-register via GET /register. The registration form requires:

  • Name, email, password
  • Department — selected from active departments
  • Declared level — hod or employee (stored in declared_level)

On submission, the account is created with is_approved = false and role = 'employee' as defaults. The user cannot log in until an admin approves the account. At approval, the admin sets the final role (which may differ from the declared level — e.g., a user declaring "hod" may be approved as "employee" if another HOD already exists for that department).

Unapproved account blocking is enforced in LoginController — after standard credential validation, it checks $user->is_approved and returns an authentication error if false, regardless of correct password.

5.2 Event Management

Events are the central organising unit. Each event belongs to a planning week and carries rich metadata about its schedule, logistics, and participants.

Planning Weeks

Admins manage planning weeks at GET /admin/planning-weeks. Weeks can be created manually or imported in bulk from a CSV file via GET/POST /admin/planning-weeks/import. Only one week can be "current" at a time; PATCH /admin/planning-weeks/{week}/current sets a week as current and unsets all others.

Event Creation Workflow

At GET /admin/events/create, the admin fills in event metadata (name, type, date, venue, coordinator, etc.). Crucially, when the event type is selected, an AJAX request fetches matching event_type_requirements rows grouped by department and renders a pre-populated checklist. The admin can:

  • Check/uncheck individual requirements to include or exclude them
  • Override the priority for any individual item before saving
  • Override the deadline for any individual item
  • Add custom requirements beyond the template

On POST /admin/events, the controller creates the event record, then bulk-inserts the selected requirements as requirements rows linked to both the event and their respective departments.

Event Show Page

At GET /events/{event}, all authenticated users see the event's requirements grouped by department. HODs and employees see their own department's checklist with update controls; other departments are shown in read-only mode. Admins see all departments with full controls.

5.3 Requirement Management

Requirements are the atomic unit of readiness. Each requirement represents one task a department must complete for an event to proceed smoothly.

Status Updates (AJAX)

The status update uses PATCH /requirements/{requirement}/status without a full page reload. Alpine.js sends the request and updates the DOM in place, changing the status badge and triggering a recalculation of the readiness bar. This provides a fluid, responsive UX even on slow connections.

Assignment

PATCH /requirements/{requirement}/assign sets the assigned_to foreign key. This links a specific user (from the same department) to a requirement, making accountability explicit at the individual level rather than just the department level.

Escalation

PATCH /requirements/{requirement}/escalate sets is_escalated = true and records escalated_at. Escalated items appear in the Critical Alerts panel regardless of their priority, and are highlighted throughout the UI. Escalation can be triggered manually by an HOD or automatically by the system when a Critical/High requirement passes its deadline without being completed.

5.4 Priority System

The priority system is the backbone of the weighted readiness calculation. It ensures that completing trivial tasks cannot mask the presence of unresolved critical blockers.

Priority Levels & Weights

Critical5Red (bg-red-100 / text-red-700)1 (highest urgency)
High3Orange (bg-orange-100 / text-orange-700)2
Medium2Amber (bg-amber-100 / text-amber-700)3

Weighted Readiness Formula

The weighted readiness percentage is calculated per department per event:

Weighted Score = ∑(priority_weight × status_readiness_weight)
Weighted Max = ∑(priority_weight)
Weighted Readiness % = (Weighted Score ÷ Weighted Max) × 100

Where status_readiness_weight is the partial-completion value from the RequirementStatus enum (see Section 10). A requirement with status "approved" (0.8) contributes 80% of its weight, while "in_progress" (0.5) contributes 50%.

At-Risk Detection

An event is flagged as "at risk" when it has 2 or more requirements with:

  • Priority = Critical or High
  • Status not in [completed, approved]
  • deadline <= event_date (i.e., the deadline has passed or the task must be done before the event)

5.5 Deliberations

The deliberation module provides a formal, documented process for resolving requirements that cannot be actioned unilaterally — for example, decisions that require budget approval, policy exceptions, or cross-departmental coordination.

Lifecycle

  1. A user (any role) creates a deliberation at POST /events/{event}/deliberations — typically linked to a specific requirement via requirement_id
  2. Status starts as open
  3. Participants are added; threaded comments are used for discussion
  4. Supporting documents are attached via file upload
  5. A recommendation is recorded
  6. An admin or director approves (POST .../approve) or rejects (POST .../reject) via DeliberationApprovalController
  7. On approval, status moves to closed with decision_made = true and approved_by set
  8. Unresolved deliberations can be escalated (PATCH .../escalate) to status escalated

Impact on Readiness

Requirements that are "under deliberation" get a status_readiness_weight of 0.2, reflecting that work is happening but the outcome is uncertain. Once approved or completed, the weight jumps to 0.8 or 1.0 respectively, improving the event's readiness score.

WebSocket Channel Authentication

All chat channels are private channels. The channel name is chat-room.{id}. When the browser Echo client subscribes, Laravel handles the auth request and calls ChatRoomChannel::join():

// app/Broadcasting/ChatRoomChannel.php
public function join(User $user, ChatRoom $chatRoom): bool
{
    return $chatRoom->canAccess($user);
}

The canAccess() method on the ChatRoom model checks the room type and user role/department to determine membership.

Typing Indicators

Typing indicators use Reverb's whisper feature — client-side ephemeral events that are not stored in the database. When a user starts typing, the Echo client whispers a typing event with the user's name to all other subscribers. The indicator automatically fades after a timeout.

Unread Badge

The navigation bar shows a badge with the count of rooms that have unread messages. The frontend polls GET /chat/unread on an interval and updates the badge count. Clicking the badge reveals a popup listing the rooms with unread messages and the count per room. Opening a room triggers PATCH /chat/{room}/read, which updates chat_room_user.last_read_message_id to the latest message ID.

The admin panel lives under /admin and is protected by the role:admin middleware. It uses a dedicated sidebar layout separate from the main application layout.

Visitor Analytics

The TrackPageVisit middleware writes to the page_visits table on each request — capturing the URL path, IP address, user agent, and authenticated user ID (if any). The admin dashboard aggregates these into a 7-day bar chart rendered with Alpine.js, showing daily visit counts. This provides basic usage analytics without requiring a third-party tool.

Staff Performance

The staff performance view (GET /admin/staff) shows a table of all HOD and employee users with their task completion statistics: total requirements assigned, completed count, completion rate %, and overdue count. This enables management to identify individuals who may need support.

5.8 Notifications & Reminders

Laravel's notification system is used for in-app and email alerts. Notifications are stored in the standard notifications table (polymorphic) and optionally dispatched to the user's email address.

Reminder Workflow

Any HOD or admin can trigger department reminders for an event via POST /events/{event}/reminders. ReminderController queries all incomplete requirements for the relevant department, builds a notification containing the full list of pending tasks, and dispatches it to each department user via the database and mail channels.

Notification Centre

The bell icon in the navigation header shows a badge with the count of unread notifications. GET /notifications shows the full notification list; PATCH /notifications/{notification}/read marks a single notification read; PATCH /notifications/read-all marks all as read.

5.9 Audit & Reporting

Audit Log

Changes to requirements and events are written to the audit_logs table. Each row captures the acting user, the action performed, the model type and ID, and JSON snapshots of old and new values. The admin audit log view at GET /admin/audit-log displays a filterable and paginated list of all audit entries.

CSV Export

GET /events/{event}/export generates a CSV file containing all requirements for the event, grouped by department, with their current status, priority, deadline, responsible officer, and completion state. This can be imported into Excel or shared with stakeholders who do not have system access.

Print Report

GET /events/{event}/print renders a print-optimised Blade view with all event details and department requirement tables. Browser print or PDF export produces a clean A4 document suitable for physical distribution in planning meetings.

Post-Event Reviews

The post_event_reviews table stores retrospective reviews after an event concludes. Reviews capture an overall rating, freeform notes, and lessons learned, providing an institutional knowledge base for future event planning.
